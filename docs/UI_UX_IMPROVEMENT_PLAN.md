# UI/UX分析・改善計画

- 作成日: 2026-09-28
- 対象: 家族タスクアプリ / 調査時コミット `36d4301`
- 状態: 調査・計画作成済み。改善実装は未着手。

## 1. 結論

優先するのは、**タスクを見失わないこと、失敗しても入力を失わないこと、タッチ以外でも主要操作を完了できること**。

現状は、共有タスクの楽観的更新、起動時キャッシュ、カテゴリ切替、定番品、再提案など、日常利用を速くする仕組みがある。一方で、成功・失敗の表示と保存結果の不一致、表示範囲によるタスクの見落とし、共通シートの操作支援不足が残っている。配色や余白の全面刷新より、これらの解消を先行する。

特に先に対応する項目は以下。

1. 保存失敗時の入力保持と、定番品追加時の誤った成功表示を解消する（UX-01）。
2. カテゴリ削除後の未分類タスクと、最近の完了がない場合の過去履歴への導線を確保する（UX-02、03）。
3. 定番品の編集・削除・検索で一覧が壊れる条件を修正する（UX-04）。
4. シート、チェック操作、ズーム、文字色の共通基盤を整える（UX-05〜08）。

## 3. 維持する長所と設計方針

- タスクの楽観的更新と削除Undo、起動スケルトン、永続キャッシュ、遅延ロードを維持する。失敗時の回復経路を加えて信頼性を高める。
- タスク・カテゴリ・定番品のRealtime購読、再接続・画面復帰時の再取得は実装済み。今後は同期状態の説明と競合時の挙動を補う。
- 暖色の背景、控えめな境界線、用途を絞ったアクセント色を維持し、読みやすさを満たす色・サイズに調整する。
- 一括削除の確認ダイアログにはPortal、初期フォーカス、Escape対応がある。これを共通シートにも展開し、フォーカス閉じ込め・復帰を追加する。
- 日付の「今日・明日」、タイトル候補、定番品のワンタップ追加は残す。片手操作と手数の少なさを損なわない。

既存の[デザイン基準](../DESIGN.md)は実装の参照元として継続利用する。ただし、低コントラスト文字を補助情報なら許容する説明や、ズーム禁止の仕様はUX-07、08に合わせて改訂する。打ち消し線やアイコンの併用だけでは文字の読みやすさを保証できない。

## 5. 詳細な改善項目

### UX-01 保存結果に合わせて表示を更新する

**コード確認。** [作成フォーム](../src/components/task/task-create-sheet.tsx#L60)は`onSubmit`を待たず入力を消して閉じ、[詳細](../src/components/task/task-detail-modal.tsx#L50)も保存結果を待たず閉じる。[親画面](../src/app/page.tsx)のハンドラはhookが返す`{ data, error }`を呼び出し側へ返していない。定番品の作成・編集も同様。[定番品からの追加](../src/components/staple/staple-items-sheet.tsx#L105)は成功前に利用回数を更新し、成功トーストを表示する。カテゴリ管理は`await`していても設定画面が結果を捨てるため、失敗時にもフォームを閉じる。

**影響:** 回線不良時に入力をやり直す。追加成功と失敗が続けて表示される。送信中の連打で重複追加が起き得る。

**改善:** hookから画面まで型付きの成功・失敗結果を返す。単に`await`を追加するだけでは解消しない。フォームは保存成功後に閉じ、失敗時は入力を保持して再試行を出す。ワンタップ追加は即時の仮表示を残し「追加中」として扱い、成功後のみ利用回数・成功表示を確定する。二重送信を操作単位で抑止する。

**受け入れ条件:** 作成・編集・カテゴリ保存・定番品追加を各々失敗させても入力が残る。遅延中に連打しても同じ送信が重複しない。失敗時に成功トーストや利用回数増加が残らない。

### UX-02 未分類タスクを見失わない

**コード確認・簡易再現。** [DB](../supabase/migrations/001_initial_schema.sql#L51)はカテゴリ削除時にタスクの`category_id`をnullにする。[ホーム](../src/app/page.tsx#L125)はカテゴリがあれば先頭を自動選択し、[カテゴリタブ](../src/components/category/category-tabs.tsx#L34)には「すべて」「未分類」がない。別カテゴリが残る状態でカテゴリを削除すると、削除元タスクを一覧から開く導線がなくなる。最後のカテゴリを削除した場合も古い選択IDが残る条件がある。

**改善:** 常時「すべて」への導線を用意し、未分類を明示して再分類できるようにする。nullを「すべて」と「未分類」の両方に使わず、フィルタを明確に区別する。カテゴリ削除時は対象タスク・定番品の件数と移動先を示す。カテゴリ必須という既存編集方針を維持する場合も、過去・削除由来の未分類データの救済は必要。

**受け入れ条件:** 2カテゴリから1つ削除、最後のカテゴリ削除、他端末から削除、カテゴリ0件、未分類定番品から追加の全条件で、タスクを発見・再分類できる。

### UX-03 完了履歴をいつでも開き、表示範囲を正しく伝える

**コード確認・簡易再現。** [取得](../src/hooks/use-tasks.ts#L12)は直近30日の完了を初期対象とする一方、[もっと見る](../src/components/task/task-list.tsx#L214)は選択カテゴリの読み込み済み完了が1件以上あるときしか表示されない。古い完了だけのカテゴリでは履歴を開けない。「すべて削除」は[現在のフィルタ済み・取得済みタスク](../src/app/page.tsx#L185)だけが対象。

さらに履歴追加は世帯全体でページングし、現在カテゴリの該当がないページもある。カーソルは`completed_at`だけなので同時刻がページ境界に並ぶと取りこぼし得る。通常の再取得は初期30日分の配列へ置き換えるため、読み進めた古い履歴が消える可能性がある。

**改善:** 未完了一覧と完了履歴を分離し、0件でも履歴を開ける導線を置く。カテゴリ条件、取得期間、件数の意味を明記する。履歴をページ単位で保持し、日時とIDによる安定したカーソルを使う。削除はまず「表示中の完了N件を削除」とし、世帯全件削除を実装する場合は別仕様・別確認にする。

**受け入れ条件:** 最近の完了0件でも31日以上前の履歴へ到達できる。同一完了時刻が30件を超えても重複・欠落なく辿れる。再接続後も履歴の閲覧位置を保つ。削除確認の件数・カテゴリ・範囲と実際の対象が一致する。

### UX-04 定番品の編集一覧を壊さない

**コード確認・簡易再現。** [並び順適用](../src/components/staple/staple-items-sheet.tsx#L99)で`find`が返す`undefined`を`si !== null`では除外できない。その後の`si.id`参照が例外になる。編集開始後の削除、検索結果を残して編集へ切り替えた場合などが該当する。新規追加も固定された`orderedIds`に含まれず編集一覧から落ちる。

**改善:** 存在するIDだけで並び順を導出し、新規IDを末尾に補う。検索結果と全体の並び順を区別する。保存失敗・Realtime変更でもローカル順序とデータを再整合する。

**受け入れ条件:** 編集中の追加・削除・他端末削除、検索後の編集切替、並べ替え失敗で画面が落ちず、存在する品目が一度ずつ表示される。

### UX-05 共通シートを操作可能なダイアログにする

**コード確認。** [BottomSheet](../src/components/ui/bottom-sheet.tsx)、[Modal](../src/components/ui/modal.tsx)にはdialogの意味付け、Escape、フォーカス閉じ込め・復帰、明示的な閉じるボタンがない。[ConfirmDialog](../src/components/ui/confirm-dialog.tsx)には一部対応があるが、閉じ込め・復帰はない。各部品が独立して`body.style.overflow`を空に戻すため、子シートを閉じると親が開いたままスクロールロックが解除される構造。

**改善:** 共通Overlay基盤にPortal、dialog名、初期フォーカス、Tab循環、Escape、閉じるボタン、呼び出し元への復帰を集約する。最前面だけを操作対象にし、重ね表示を考慮したスクロールロック管理を導入する。未保存変更の扱いと閉じる理由を共通化する。

**受け入れ条件:** タスク作成・詳細・並べ替え・定番品・写真トリミング・確認ダイアログで同じ操作規則が働く。子を閉じても親のフォーカス・背景ロックを保ち、すべて閉じると元のボタンに戻る。

### UX-06 主要操作をキーボードと読み上げで完結させる

**コード確認。** [タスクカード](../src/components/task/task-item.tsx#L143)はクリック可能なdivで、チェックボタンは名前・チェック状態を持たない。[定番品](../src/components/staple/staple-item-card.tsx#L101)の通常追加はpointerイベントのみで、Enter/Spaceのクリックでは実行されない。タスク・カテゴリ・定番品のDnDにキーボードセンサーがなく、カテゴリハンドルはTab移動対象外。色選択、カテゴリ選択、通知スイッチなどの名前・状態も不足する。

**改善:** 詳細を開く操作と完了操作を別々の意味のある要素にする。完了はラベル付きcheckbox等、通知は名前付きswitch、カテゴリは選択状態を伝えるボタンまたは適切なタブパターンにする。定番品追加をclickでも実行し、長押しの代替「数量を変えて追加」を設ける。並べ替え・画像の位置調整にキー操作または移動ボタンを用意する。

**受け入れ条件:** ポインターを使わず、追加・詳細・完了・削除・数量変更・並べ替え・通知設定を完了できる。読み上げで項目名と選択・完了状態が分かる。ボタンの入れ子を作らない。

### UX-07 ページの拡大を許可する

**コード確認・要実機検証。** [viewport](../src/app/layout.tsx#L58)に`maximumScale: 1`、`userScalable: false`が指定されている。拡大制限の実際の適用はブラウザによる。

**改善:** 拡大制限を外す。小さい入力文字によるモバイルの自動ズーム対策は、入力文字サイズやレイアウト側で解決する。DESIGNのviewport仕様も更新する。

**受け入れ条件:** 対応端末でピンチ拡大でき、200%の文字・ページ拡大時も保存・閉じる・戻るに到達できる。

### UX-08 情報を担う文字のコントラストを確保する

**コード確認・計算済み。** [色定義](../src/app/globals.css)と使用箇所を確認。空状態、作成者、完了件数等に`text-subtle`、今日の期限に小さい`text-warning`、コピー成功・メール送信完了に`text-success`が使われる。[カテゴリ選択](../src/components/task/category-picker.tsx)は全カテゴリ色に白文字を重ねる。

| 前景 / 背景 | 算出比 | 主な問題 |
|---|---|---|
| subtle `#a39e98` / 白 | 2.658:1 | 補足文・完了タイトル・入力ヒント |
| subtle / 背景 `#f6f5f4` | 2.441:1 | 空状態 |
| warning `#dd5b00` / 白 | 3.770:1 | 小さい期限文字 |
| success `#1aae39` / 白 | 2.934:1 | 成功メッセージ文字 |
| 白 / カテゴリ黄 `#eab308` | 1.918:1 | 選択中カテゴリ |
| 白 / カテゴリ緑 `#22c55e` | 2.279:1 | 選択中カテゴリ |

値は不透明な色同士の相対輝度から算出。半透明の面上は合成後の色を別途検証する。通常文字4.5:1、大きい文字3:1を基準にする。補足情報やプレースホルダも自動的な適用除外にはならない。[W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**改善:** 読ませる補足文はmuted相当以上へ。warning/successは文字用と面・装飾用を分ける。カテゴリは色チップ＋濃い文字、または背景ごとに適合する前景色を選ぶ。完了は打ち消し線とチェックで区別しつつ読める濃さを保つ。

**受け入れ条件:** 実際の背景との組み合わせを測定し、通常サイズの情報文字は4.5:1以上。全プリセット色、選択・未選択・完了・エラー状態を確認する。

### UX-09 押しやすいサイズと見えるフォーカスを統一する

**コード確認・要実機検証。** 設定の戻るは24pxアイコンのみ、ホーム設定は約32px相当、カテゴリ編集・削除は約24px、[定番品削除](../src/components/staple/staple-item-card.tsx#L93)は20px。カテゴリ・日付チップ、色選択も既存DESIGNの40px目安に届かない。Buttonに共通の最小高さ・focus-visible規定がない。

**改善:** IconButton・Button・選択チップに共通の当たり判定を設定する。プロジェクト目標は補助操作40px以上、主操作44〜48px。大きな当たり判定同士が重ならない余白も確保し、フォーカスリングを統一する。WCAG 2.2 AAの最小ターゲット基準24 CSS pxと例外条件とは区別する。[W3C: Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### UX-27 作成者を担当者と誤解させない

**コード確認・改善仮説。** 一覧の名前は`created_by`のニックネームだが役割ラベルがない。担当者の型・DBテーブルは存在する一方、現行タスクUIには担当設定がない。完了者を示す入力・表示経路もない。

**改善:** まず「追加: ○○」等と役割を明示する。担当割当や完了者表示は「誰がやるか分からない」という利用上の課題を確認してから導入する。実装する場合は任意担当・未割当を基本とし、通知、DB権限、Realtime、移行をまとめて設計する。

**受け入れ条件:** 既存表示で作成者と担当者が混同されない。機能追加時は2人の利用者が担当変更・完了者を同じ意味で理解でき、担当なしでも従来どおり使える。

## 6. 推奨する画面構成

機能を増やす前に、主要な行動の入口を整理する。以下は設計案であり、完成画面・検証済みの仕様ではない。

| 画面 | 上部 | 主領域 | 主操作・補助操作 |
|---|---|---|---|
| ホーム | 家族名、メンバー概要、設定、必要時だけ同期状態 | すべて/カテゴリ、必要時の検索、未完了一覧、独立した完了履歴導線 | 追加FAB、名前の分かる定番品導線、並び替え |
| 空のホーム | 通常と同じナビゲーション | 本当に0件なら短い説明と「タスクを追加」。通信失敗なら理由と再試行 | 初回のみ家族を招待する案内 |
| タスク入力 | タイトルと閉じる | タスク名、カテゴリ、期限、任意のメモ・リンク | 保存状態を持つ主ボタン。未保存なら破棄/編集継続 |
| 定番品 | 検索、管理への入口 | 名前・数量を優先したカード。追加先と追加結果を明示 | ワンタップ追加、数量変更の明示導線 |
| 設定 | ホームへ戻る | プロフィール、家族グループ/招待、通知、カテゴリ | セクションごとの保存状態とエラー |
| 初回利用 | 家族グループ作成/参加の選択 | 必要最低限の入力と招待説明 | 作成/参加後に最初のタスクへ |

## 7. 実施計画

1名の実装担当を想定した目安。共通部品の再利用を前提とし、優先項目を小さな変更に分ける。着手前に再現用データを固定し、各フェーズの受け入れ条件を満たしてから次へ進む。確定した日程・担当者の割当ではない。

| フェーズ | 内容・対象ID | 成果物 | 主担当の役割 | 概算 |
|---|---|---|---|---|
| 0: 再現と仕様確定 | P1の再現、端末確認、表示フィルタ/履歴/保存結果の契約 | 再現データ、画面状態表、基準スクリーンショット | 実装担当＋UX確認者 | 1〜2日 |
| 1: 情報と入力を守る | UX-04、01、02、03、12、13、20 | 失敗回復、履歴アクセス、定番品修正、認証復帰、回帰テスト | フロント＋必要に応じDB担当 | 10〜15日 |
| 2: 共通操作基盤 | UX-05、06、07、08、09、10、11、23 | 共通Overlay/操作部品、色・サイズ改訂、端末・読み上げ検証 | フロント＋UX/QA | 8〜12日 |
| 3: 日常の摩擦を減らす | UX-14、15、17〜19、21、22、25、26 | 入力・招待・設定・提案・一覧の改善、利用者検証 | フロント＋UX確認者 | 6〜10日 |
| 4: 検証して拡張 | UX-16、24、27 | 検索/PWA/担当機能の採否と個別仕様 | プロダクト判断＋フロント/DB | 別見積り |

フェーズ0〜3は概算25〜39人日。端末検証結果や競合制御の方式によって変動する。機能拡張を同時投入せず、まずP1を解消する。UX-16の検索はフェーズ4で採否を検証するが、探索の困難が確認されればフェーズ3へ繰り上げる。

### 最初に切り出す実装単位

1. **定番品一覧の破綻修正（UX-04）**: 最小の再現テストとデータ整合の修正。
2. **保存結果の共通契約（UX-01）**: hook→親→フォームを一貫させ、タスク/定番品/カテゴリを順次移行。
3. **未分類の救済（UX-02）**: フィルタ型、カテゴリ削除時の説明、0カテゴリ状態を含める。
4. **履歴導線と削除範囲（UX-03）**: 到達不能を先に修正し、ページ保持・カーソルを次の変更で整える。
5. **状態表示と競合回復（UX-12、13）**: 読込失敗→再試行、操作単位の回復、2端末検証。
6. **認証復帰（UX-20）**: callback失敗表示と既存セッション中の復旧を一組で検証。

共通Overlay（UX-05）の設計は早期に固める。P1完了判定にはUX-05〜08も含み、フェーズ1だけで全P1完了とはしない。

### 依存する技術判断

- フォーム送信は「成功して閉じる」を基本にし、即時追加は仮表示＋失敗回復を許容する。保存済みと未送信の見た目を区別する。
- 「すべて」「未分類」「個別カテゴリ」は別の状態として扱い、追加先カテゴリとは分離する。
- 履歴は現在の単一配列キャッシュへの追記方式を再検討し、背景再取得でページが失われない設計にする。
- 競合検知にDB変更が必要なら新しいマイグレーションと型生成、RLS確認を行う。既存マイグレーションを編集しない。
- 完全オフライン保存、担当者、永続的なごみ箱は別仕様。単純なUI修正に含めて約束しない。

## 8. 検証計画と完了条件

### 自動検証

既存CIはVitest、ESLint、TypeScriptを実行する。既存のtask-listテストには「完了がある状態でのもっと見る」はあるが、「最近の完了0件で古い履歴だけある」条件はない。ConfirmDialogもEscape・PortalのテストはあるがTab循環・フォーカス復帰はない。既存テストを維持し、以下の失敗条件を中心に追加する。

| 対象 | 追加する価値のある回帰テスト |
|---|---|
| 保存（UX-01） | 遅延/失敗時の入力保持、連打、誤成功表示、成功後のみ利用回数更新 |
| 分類/履歴（UX-02、03） | カテゴリ削除、未分類救済、直近完了0件、同日時ページ境界、背景再取得 |
| 定番品（UX-04、14） | 編集中削除/検索/追加、初期値切替、数量・メモの明示クリア |
| Overlay/操作（UX-05、06） | role/name、Tab循環、Escape、復帰、入れ子ロック、キーボード追加 |
| 状態/同期（UX-12、13） | キャッシュなし失敗、再試行、並行成功と失敗、未取得タスクの復活 |
| 認証/通知（UX-20、21） | callback理由、既存セッション中の復旧、解除API失敗の伝達 |
| 動き/日付（UX-23、26） | reduced-motionでも切替完了、本人操作以外で演出しない、タイムゾーン境界 |

主要フローには実ブラウザの操作テストを追加する。自動アクセシビリティ検査は補助として使用し、読み上げやジェスチャーの確認を代替したとみなさない。単にclass名や実装内部を再確認するテストは増やさない。

### 手動検証マトリクス

| 軸 | 条件 |
|---|---|
| 画面/端末 | 320/375/390px、タブレット768px、デスクトップ1280px。iOS SafariとPWA、Android Chrome、デスクトップChrome/Safari |
| 入力方法 | タッチ、マウス、キーボードのみ、VoiceOver/TalkBack、200%拡大、動きを減らす設定 |
| データ | 0/1/50/多数件、未分類、カテゴリ0/10件、長い文字、直近完了0件、31日以上前の履歴、同時刻の履歴 |
| 通信 | 正常、数秒遅延、取得/保存失敗、オフライン、キャッシュ有無、アプリ復帰、WebSocket再接続 |
| 共同利用 | 2端末同時編集、他者削除、カテゴリ変更、古い完了の未完了化、片側保存失敗 |
| 入力中の状態 | キーボード開閉、長文スクロール、子シート開閉、戻る/閉じる、保存中の離脱 |

各対応PRでは、対象IDの受け入れ条件、画面の前後比較、関連テスト、実機確認の結果と未確認範囲を残す。P1完了の条件は、単にエラーが出なくなることではなく、対象の操作が完遂でき、失敗時に回復できること。

### 評価指標

基準値は未計測。フェーズ0で固定条件の測定を行い、改善前後を比較する。以下の数値は達成済みの結果ではなく、採用判断のための初期目標。

| 指標 | 計測方法・初期目標 |
|---|---|
| 入力保全 | 保存失敗シナリオで入力消失0件、失敗時の成功表示0件 |
| 到達性 | 未分類・過去履歴・通知対象に関する定義済みシナリオをすべて完遂 |
| 主要操作 | キーボードだけで追加・詳細・完了・取り消しまで完遂 |
| 探索時間 | 同じ50件のデータで対象探索時間の中央値を測り、検索等の採用案で20%以上短縮を目安にする |
| 初回利用 | 初見利用者5人程度で作成/参加と最初の共有を観察。4人以上が介助なく完了することを初期目標にする |
| 読みやすさ・操作サイズ | 通常の情報文字4.5:1以上、当たり判定は本計画のプロジェクト目標に適合 |
| 体感速度 | コールド/ウォーム起動、シート初回表示、追加完了、2端末反映を同じ回線・端末で計測。現行の即時反応を悪化させない |
| レイアウト安定性 | 提案到着・設定読込・キーボード表示で押下対象が意図せず移動/隠蔽されない |

少人数の結果から統計的な効果を断定しない。計測イベントを導入する場合も、タスク名・メモ・招待コード・メールアドレスを記録せず、操作種別・成否・時間を中心にする。
