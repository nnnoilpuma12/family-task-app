# 操作・再同期の性能改善 — 2026-10-02

[PR #99](https://github.com/nnnoilpuma12/family-task-app/pull/99) の調査を受け、マージ後の `80237c3` から `perf/responsive-task-interactions` で実装した。対象は日常操作の通信待ち、一覧の再描画、再同期・おすすめ計算の重複、タスク並び替えの書き込み量。

## 変更と検証結果

| ケース | 変更前 | 変更後 | 検証条件 |
|---|---|---|---|
| 100件中1件のタイトル変更 | 100行再実行 | 1行再実行（99%減） | 実際の `TaskList` / `TaskItem` / DnDを使用。Motionのみモック、happy-dom |
| 同じpropsで親を再描画 | 100行再実行 | 0行再実行 | 上と同じ。DnDのセンサー設定・ID配列の参照も固定 |
| 100件の隣接2件を入れ替え | RPCの対象100行 | 対象2行（98%減） | 元のsort_orderが0〜99の場合。RPCリクエスト数は前後とも1回 |
| 変更のない並び替え | 全行を更新 | リクエストなし | 並び順が正規化済みの場合 |
| 同時期の購読成立・画面復帰・online通知 | 再取得がキャンセル・再発行され得る | 各クエリ1回に集約 | 50msの集約窓内に通知。実際のTanStack Queryで確認 |
| 自分の操作とおすすめ更新通知 | 操作直後＋Realtime後の再集計 | 最後の通知から2秒後に1回 | 同じ2秒窓内の通知。取得中の変更は後続の1回で回収 |
| 追加・保存・削除のフォーム | 通信応答後に閉じる | 同じ操作イベント内で閉じる | 500ms後に応答／例外になるテストで、時刻を進める前に閉じることを確認 |

行の再実行数は変更前のmainを一時ディレクトリへ取り出して同条件で比較した。初期マウント回数は比較対象外。前回の調査ではDnDもモックにしていたため、「同じpropsでの再描画」は0だった。今回は実際のDnDを含めた検証により、毎回新しく作っていたセンサー設定も全行再描画の原因と確認できた。

これらは関数実行数、送信対象行数、制御された遅延での動作検証である。500msは本番ネットワークの実測値ではなく、画面のアニメーション・実機INP・LCPの測定でもない。API自体の処理時間やSQLは今回変更しておらず、[前回のローカル通信測定値](network-critical-path-2026-10-01.md)を改善後の値として流用しない。

## 実装の要点

- `useTasks` の操作関数の参照を固定し、操作時点の最新キャッシュを読む。`TaskItem` が自分の完了状態を通知するため、一覧のトグル関数はtasks配列に依存しない。SortableContextのID配列とセンサー設定も安定させる。
- フォームは入力を受け付けると閉じ、一覧の楽観的更新を表示する。失敗した入力は時間制限なしのトーストの「入力を復元」から戻せる。別の入力中に古いフォームを勝手に開かない。これは現在の画面内での復元であり、再読み込み後まで永続するオフライン送信キューではない。
- 同じタスクへの書き込みを直列化し、追加直後の編集・削除がINSERTを追い越すのを防ぐ。別タスクへの通信は並行する。先行応答が後続の楽観的な入力を消さないようにマージし、失敗時も別タスクの更新を丸ごと巻き戻さない。
- Homeでは購読成立・可視化・online復帰を同じ再同期処理へ渡す。Homeの対象クエリだけReact Queryの自動focus/reconnect取得を無効化する。設定画面などの通常の取得動作は維持する。
- 初期取得中に購読が成立した場合は、進行中の取得が終わってから新しいスナップショットを取る。単純に相乗りして購読前の変更を落とすことはしない。この場合の「初期取得＋再同期」の2回は必要な取得である。
- tasks・categories・staple_items・タイトル候補・おすすめの取得にAbortSignalを接続し、クエリのキャンセルをHTTP要求まで伝える。DB側で実行開始済みの処理が必ず中断するという保証ではない。
- おすすめの更新予約を1箇所へ集約。自己INSERTのechoと、キャッシュに存在するタスクの並び順・URL・期限だけのRealtime更新では再集計しない。取得していない履歴の更新は保守的に再集計する。追加済みの候補は楽観的キャッシュから即座に非表示にする。
- 並び替えは変更されたsort_orderだけを既存RPCに渡す。所属判定にはSetを使い、毎行のincludes検索をなくす。DBマイグレーションは不要。

## 引き続き残る項目

今回の範囲で調査の全項目が解消したわけではない。次の変更は別の設計・測定が必要。

1. プロフィールを起点にする初回取得の直列経路とページ間のキャッシュ共有。
2. 全カラム取得の削減、履歴の複合カーソル、取得上限1000件、長大な一覧の仮想化。
3. 初期JSの分割、タブ切替の固定待ち、キャッシュ永続化の非同期化、PWAシェルキャッシュ。
4. カテゴリ・定番品の並び替えの差分更新、通知経路の直列参照。
5. 本番相当の回線と実機でのLCP・INP・操作から表示までのp50/p95測定。

特に初期取得は `is_done / sort_order / created_at` で並ぶため、1000件で打ち切られた集合の最古completed_atだけを使って全履歴を正しく辿れるとは限らない。今回の通信削減を理由に取得上限を下げる変更はしていない。
