# 世帯情報の整合性・テスト網羅性調査

調査日: 2026-10-20。対象: ローカルのアプリ実装、SQL migration 001〜029、Vitest、DB smoke、Playwright、CI。実稼働DBの適用状況は未確認。

## 実装状況（2026-10-21）

以下のP0対策を migration 030 とクライアントへ実装した。この文書の「主な指摘」は修正前の調査記録として残している。

- 既所属者による別世帯への招待参加をDBで拒否。同じ世帯への再送は冪等に成功
- create/joinでプロフィール行をロックし、同一ユーザーの並行操作を直列化
- profiles/householdsをRealtime対象に追加し、focus/visibilitychange/onlineでも再取得
- データ取得前に最新プロフィールの所属を確認し、旧世帯IDの先行利用を廃止
- 所属相違時に永続・in-memoryキャッシュを破棄し、別タブにも伝播
- 世帯名の同時編集をupdated_atで検出し、古い画面からの上書きを防止
- プロフィール取得エラー時にupsertへ進まないよう修正

受入テストは `use-page-data.test.ts`、`household-settings.test.tsx`、`join-form.test.tsx`、`household-cache.test.ts` とDB smokeへ追加した。実DBの検証結果は実行環境の欄を更新して管理する。

修正後の検証結果: Vitest 43ファイル・423件、型チェック、Lint、production build、Playwright 3件、ローカルDB migration全適用、pgTAP 14件がすべて成功。

## 結論

世帯名の変更は `households.id` を維持した UPDATE であり、ユーザーごとの世帯を作り直す処理ではない。名前・ニックネーム変更だけで所属が分裂する経路は見つからなかった。

ただし、**パートナーに変更が反映されない問題は起こりうる**。世帯・プロフィール・メンバー情報は初回取得だけで、変更イベントや復帰時の再取得がない。また、**別世帯への参加は本人だけの所属変更として許可されている**。パートナーが自動で一緒に移る仕様ではなく、意図せず参加を行えば実際に所属が分かれる。

既存416件の単体テストが成功していても、この2種類の問題を検知できない。優先すべきはテスト件数の増加より、複数ユーザー・複数端末・所属遷移を横断する検証の追加。

- 一時的なVitest再現テスト: 3件成功。「問題が存在する現状」を assert した観察用テストであり、修正後の受入テストではない。
- 再現結果: online/focus/visibilitychange後も所属・世帯名・メンバーが古いまま。同一ユーザーのキャッシュ所有者確認では旧世帯キャッシュが残る。プロフィール取得エラーでも upsert へ進む。

## 主な指摘

### F1 / 高: 世帯情報・メンバーの変更が他端末へ反映されない

根拠: `src/hooks/use-page-data.ts:37` の effect は初回・オプション変更時のみ実行する。`src/hooks/use-realtime-resync.ts` が再取得するのは tasks/categories/stapleItems だけ。migration のRealtime publicationも tasks/categories/staple_items のみ。households/profiles の購読はない。

再現: AとBが同じ世帯Hのホーム/設定を開く。Aが世帯名を変更する、プロフィールを変更する、または別ユーザーがHに参加する。Bのページを維持しても世帯名・メンバー一覧は更新されない。復帰イベントを発生させても usePageData は再取得しない。通常は再マウント/再読込で再取得されるが、読込成功が前提。

影響: 見た目の世帯不一致、古いメンバー一覧・担当者候補。プロフィール変更も同じ構造。DB上の所属分裂とは区別する。

不足: 2ユーザー間の世帯名・プロフィール・参加/移動反映、復帰時再同期テスト。観察用テストでhook単体の再取得欠如を確認済み。ブラウザ2台の実証は未実施。

### F2 / 高: 既所属者の招待参加は本人だけを別世帯へ移す

根拠: `supabase/migrations/011_restore_rpc_auth_checks.sql:214` の join RPC は現在の所属確認なしに本人の `profiles.household_id` を上書きする。`src/app/household/join/page.tsx` とmiddlewareには既所属者の参加拒否がない。`join-form.tsx` に移動元や影響の表示・確認もない。029には移動時の旧参照掃除があり、移動そのものは想定された挙動と読める。

再現手順: H1にA/Bを所属させ、Aが `/household/join` を直接開きH2の有効コードを送る。SQL上、AのみH2、BはH1に残る。パートナーをまとめて移す処理はない。Bの古いメンバー表示もF1により残りうる。

これは現仕様の結果であり、直ちに「実装バグ」とは断定しない。既所属者の参加を禁止するか、本人だけの移動として明示的に許可するかの仕様を先に定め、DB側でも保証する必要がある。パートナーを無条件に追従移動させる修正は避ける。

不足: 未所属→参加だけでなく、同世帯再参加・別世帯移動・旧世帯側の残存データと権限まで検証するDB/E2E。既存フォームテストはRPC結果をモックしており所属変化を検証しない。

### F3 / 高: 別端末での所属変更を同一ユーザーのキャッシュが検知しない

根拠: `src/lib/cache-identity.ts` の識別子はuserIdのみ。`src/app/providers.tsx` はその判定で永続データの復元を許可。`src/app/page.tsx:80` はプロフィール確定前にキャッシュ済み世帯IDでクエリ・購読を開始する。参加フォームのキャッシュ消去は操作したタブのQueryClientとそのブラウザのstorageに限定される。他タブのメモリを更新するstorage/BroadcastChannel処理もない。

再現手順: Aの端末1/2をH1で開く。端末1でH2へ移動。端末2はページを維持するとH1のprofile/stateを保持。再起動時も同一userIdなのでH1キャッシュを信頼し、最新プロフィール到着前に旧データを使用できる。新所属取得後はクエリキーがH2へ変わるが、旧世帯クエリを全削除する処理はこの経路にはない。

影響: 旧データの残留・一時表示、旧所属での書込み試行。RLSがサーバー操作を拒否しても、端末キャッシュの表示までは消せない。オフラインで過去に取得済みのデータを表示できる仕様との境界は要定義。

不足: 同一アカウント別端末/別タブ、復元前の所属確認、移動と未完了リクエスト・楽観更新の競合。観察用テストは同一userIdで旧キャッシュを保持する事実を確認済み。画面への露出時間は未測定。

### F4 / 高: 世帯作成・参加の並行実行を直列化していない（SQL読解、未実証）

根拠: `supabase/migrations/014_fix_invite_code_extensions_schema.sql:69` は所属を通常SELECTで確認し、後からprofileを更新する。確認時の行ロック・条件付きUPDATEはない。join RPCもprofile更新前に同じロック規約を持たない。

想定順序: 未所属Aが2タブから作成→両トランザクションがNULLを読む→それぞれH1/H2を作る→profileの更新自体は行ロックで順番待ちになるが、所属確認は再実行されず後続が上書きしうる。トランザクション単体がatomicであることは、二重作成の排除を意味しない。

影響: 複数世帯・デフォルトカテゴリが生成され、各レスポンス/キャッシュの世帯IDと最終所属が食い違う可能性。create対join、join対別joinも検証が必要。

対策候補: profile行をロックしてから現在所属を判定し、create/joinで統一する。所属移動の競合時に「後勝ち」でよいかも仕様化。単なる `Promise.all` だけでなく、DBの2接続と同期点で競合順序を固定してテストする。

### F5 / 中: 未所属確定と未取得が同じフォールバックになる

根拠: `src/app/page.tsx:88` の `profile?.household_id ?? cachedHouseholdId` はprofile取得済みかつhousehold_id=nullでも旧IDを採用する。usePageDataがstorageを削除しても、Homeの `cachedHouseholdId` state は消えない。

影響: `/household/new` への遷移が完了するまで旧世帯クエリ・購読が残る可能性。特に遷移遅延/失敗時。通常の移動UIはnullを作らないが、DBの世帯削除（FK: ON DELETE SET NULL）や管理変更時に成立する。

不足: 未取得/null/有効IDの三状態を区別するHome統合テスト。期待値は「未所属が確定したら旧ID・旧データを使わない」。

### F6 / 中: 障害・古いレスポンス・設定のローカルstateが未検証

- `use-page-data.ts` はプロフィールの取得失敗と存在しない場合を同じupsert経路に流す。障害時にnicknameを書き戻す試行が起きることを観察用テストで確認。household_idを明示的にnull更新しているわけではなく、これが直接世帯分裂を起こすとは断定しない。
- 同hookにキャンセル/世代判定がなく、古いロードの完了がstateやlocalStorageへ反映される競合が未検証。
- `household-settings.tsx` のname/inviteCodeはpropsから初回だけuseStateに取り込む。同期機構を追加しても、props差替えだけでは入力欄・コード表示が更新されない。未保存入力の保持と外部変更の優先関係も必要。
- 世帯名保存時は `onUpdate(setHousehold)` だけでhouseholdName/localStorageを更新しない。新しい名前の再取得が失敗すると古いキャッシュが残る。
- create/join RPCはプロフィールUPDATEが0行でも検出しない。通常はサインアップtriggerでprofileが存在するが、欠損時の障害系では「成功IDは返るのに所属なし」が成立するSQL構造。DB実証が必要。

37は `use-task-recommendations.ts` のqueryKeyにはhouseholdIdがある一方、RPCはDBの現在所属を使うために必要。古い所属を保持した端末で再取得が起きると、キーと結果の所属の対応が崩れる可能性がある。

## 推奨する実装・検証順

1. P0の01/05/07/10/12/15を受入テストにする。H1(A/B)、H2(C)、未所属Dを分離して準備。E2Eは独立したbrowser contextを使う。DBの所属UUIDもassertし、画面の名前一致だけで成功としない。
2. 既所属者の参加方針を定め、RPC側で強制する。create/joinの並行処理とprofile欠損時も同時に修正する。
3. profile/household/membersの再取得元を統一し、Realtimeに加えて復帰時に再検証する。Realtimeだけでは切断中の更新を拾えない。購読対象追加時はpublication/RLSもDBテストする。
4. 所属変更検出時に旧キャッシュ・購読・選択中データを破棄し、世代の古い応答を無視する。未取得/未所属を区別する。同じuserIdでも所属が変わる点をProviderで扱う。
5. 残りのP1をDB/browser CIに追加。競合試験は独立接続で順序を制御し、ポーリングによる収束確認には上限時間を設定する。

オンラインの他端末へ何秒以内に反映するか、オフライン中の旧所属データをどこまで閲覧可能にするか、同時編集を後勝ちにするかは現状のコードだけでは保証仕様が決まらない。受入条件として明文化する。固定sleepで偶然通るテストや、モックの呼出し確認だけで「2人の整合性を保証した」とするテストは避ける。
