## 1. 楽観的更新の効果が入力画面に届いていない

根拠: `src/components/task/task-create-sheet.tsx:61`、`src/components/task/task-detail-modal.tsx:52`、`src/hooks/use-tasks.ts:143`。

`addTask` は通信前にキャッシュへ追加する。しかし作成シートは `await onSubmit(...)` が完了してから閉じる。編集と詳細画面からの削除も同様。裏の一覧は更新されていても、利用者は「追加中」「保存中」を見て待つ。回線が遅いほど、この待ちが操作の速さを決める。

改善: ローカルへの操作受付時にシートを閉じ、保存状態を一覧側で管理する。失敗時の再試行・入力内容の復元をセットで設計する。単に await を外すだけでは入力喪失につながる。チェック操作はすでに楽観的更新なので、この指摘と区別する。

## 2. `memo` があるのに全行を再実行する

根拠: `src/hooks/use-tasks.ts:308`、`src/app/page.tsx:159`、`src/components/task/task-list.tsx:67`、`src/components/task/task-item.tsx:31`。

原因は二段ある。

- `useTasks` の操作関数はレンダーごとに新しく作られる。Home 側で useCallback を使っても依存先の関数が変わるので、行へ渡す関数も変わる。
- `TaskList.handleToggle` は tasks 配列を依存に含む。1 件の変更で tasks が変わると、全行の `onToggle` が変わる。

100 件中 1 件だけタイトルを変更する検証で、残りの task オブジェクトと外側のハンドラを同一に保っても、100 件すべての `TaskItem` が再実行された。DnD やアニメーションを除いても発生する問題である。

改善: 操作関数を安定させ、操作時の最新データは query cache 等から参照する。TaskList のトグル関数も配列全体への依存を外す。単に useCallback を追加して tasks を依存に残すだけでは解決しない。修正後は「1 件編集時の未変更行の再実行数」を比較する。

## 3. 再同期の重複と、通信キャンセルの未接続

根拠: `src/lib/realtime.ts:21`、`src/hooks/use-realtime-resync.ts:37`、`src/app/providers.tsx:23`、各データ取得フック。

初期取得とは別に、Realtime の SUBSCRIBED で tasks / categories / staple_items を再取得する。復帰時には visibilitychange / online の invalidate、React Query のフォーカス・再接続時の取得、Realtime 再接続の refetch が重なりうる。2 秒の制限は独自 resync の中だけで、他の経路とは共有されていない。

「同じキーなら必ず重複排除される」とは限らない。インストール済み Query の `refetchQueries` は cancelRefetch が既定で true。既存データがある取得を中断扱いにして、新しい取得を開始しうることを再現した。一方、queryFn は AbortSignal を Supabase の `.abortSignal(signal)` に渡していないので、Query 側が中断しても HTTP が続く可能性がある。

改善: 再同期の要求を共通の窓口へ集約する。通信へ AbortSignal を伝播させる。進行中の取得を共有する場合も、スナップショット以後の変更を取りこぼさないよう、購読成立の順序や取得中に追加された再同期要求を管理する。現在の購読成立後の再取得を単純に削るのは適切でない。

関連: `src/lib/idle.ts:11` は requestIdleCallback を使うが、これは通信が暇になった合図ではない。タスク取得の応答待ち中にも実行され、おすすめ・サジェスト・定番品・購読開始が同時に動きうる。主要データの表示準備ができたかを別に判断する必要がある。また timeout がなく、必須の同期が遅れる可能性もある。[MDN: requestIdleCallback](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback)

## 4. おすすめの計算を何度もやり直す

根拠: `src/app/page.tsx:116`、`src/app/page.tsx:159`、`src/hooks/use-realtime-tasks.ts:44`、`src/hooks/use-task-recommendations.ts:69`、`supabase/migrations/017_recommendations_time_window.sql:58`。

追加・完了・削除の直後におすすめを invalidate する。Realtime は操作した本人にも届き、送信者や変更項目を判別せず `onRemoteChange` を呼ぶため、その後 2 秒のタイマーでも再取得しうる。並び順だけの UPDATE でも対象になる。10 分の staleTime は明示 invalidate による取得を防がない。

おすすめ SQL は直近 1 年の履歴を正規化・タイトルごとに並べ替え、間隔の配列、中央値、ばらつきを計算して最後に 5 件へ絞る。「結果 5 件」でも入力は 5 件ではない。ただし、以前の全期間集計はすでに修正されており、現在は 1 年分に限定されている。

改善: 自端末操作と Realtime の更新通知をまとめて再検証する。おすすめに影響しない sort_order / url 等の変更は除外する。まず呼び出し回数を減らし、それでも SQL が支配的ならタイトル単位の集計や世帯単位のサーバーキャッシュを検討する。

## 5. キャッシュなし起動は、JS → プロフィール → 一覧という待ち順

根拠: `src/app/page.tsx:88`、`src/hooks/use-page-data.ts:38`、`src/hooks/use-tasks.ts:26`。

ホームは静的な骨組みを返し、データ取得はブラウザの Effect / Query で開始する。householdId のキャッシュがなければ、プロフィールを取得するまで tasks / categories を取得できない。

```text
HTML 取得 → JS 読込・実行 → セッション取得 → プロフィール取得
                                              ↓
                                    タスクとカテゴリを並列取得 → 一覧
```

セッションのローカル読取は通常ネットワーク不要だが、有効期限切れでは更新通信も起こりうる。再訪では householdId と Query の永続キャッシュが効くため、同じ直列待ちとは限らない。

さらにプロフィール・メンバー・世帯情報は Query に入っておらず、設定画面との往復でも再取得する。設定の household / members は profile の後に並列取得する。

改善: 本人の profile・世帯・カテゴリ・最初の表示用タスクを返す小さな bootstrap RPC/API を検討する。全履歴やおすすめまでまとめると最も遅い処理待ちになるので含めない。profile / members / household のキャッシュを共有し、プロフィール更新時に更新・無効化する。SSR は選択肢だが、サーバーと DB の距離によって TTFB が増えるため比較が必要。

## 6. 一覧に不要なデータと、画面外の行まで扱う

根拠: `src/hooks/use-tasks.ts:35`、`src/hooks/use-tasks.ts:99`、`src/app/page.tsx:137`、`src/components/task/task-list.tsx:192`。

初期取得は全カテゴリの未完了＋直近 30 日の完了、最大 1,000 件、全カラム。長い memo / url も一覧表示時に取得し、キャッシュ保存する。画面には選択カテゴリだけを出すが、そのカテゴリの行は画面外も含めてすべて描画する。完了済みは「もっと見る」で追加するほど DOM と永続キャッシュが増える。

完了履歴の追加取得も世帯全体で 30 件ずつなので、選択カテゴリの履歴が少なければ「もっと見る」を押しても表示件数が増えないケースがある。速さ以前に無駄な待ちに感じられる。

改善: 一覧用の軽量データと詳細用データを分ける。完了履歴をカテゴリ別の安定した複合カーソルでページングする。カテゴリ間の即時切替との兼ね合いで先読み量を調整する。数百件の表示が現実的なら仮想化、あるいは完了セクションの折り畳み・表示上限を導入する。DnD と行高さ・フォーカスを含めて検証する。

注意: 現在の初期ソートは completed_at 順ではないため、1,000 件に達したときに「漏れた完了済みを最古 completed_at より前のページングで全部回収できる」とは限らない。未完了 1,000 件以上も打ち切りになる。単純に limit を下げると正確性が悪化する。

## 7. 並び替えが DB・Realtime・画面へ波及する

根拠: `src/components/task/task-list.tsx:142`、`src/hooks/use-tasks.ts:322`、`supabase/migrations/007_security_hardening.sql:132`、`src/hooks/use-realtime-tasks.ts:56`。

1 行を移動すると、表示中の未完了タスク全件の ID と連番を送る。RPC は値の変わらない行にも UPDATE し、updated_at も変える。N 件更新すると N 件分の変更イベントが発生し、受信側は各イベントで tasks 全体を map する。キャッシュが M 件なら、その配列走査だけでおおむね N×M の処理になる。React のレンダーが何回にまとまるかは別の問題であり、イベント数と必ず同数とは限らない。

`reorderTasks` 自体にも `prev.filter(... orderedIds.includes(...))` の二重走査がある。ただし先に減らすべきは DB の更新件数とイベント数である。

カテゴリの並び替えは `src/hooks/use-categories.ts:103` でカテゴリ数だけ HTTP UPDATE を並列実行する。定番品は RPC 1 本だが、`012_staple_items.sql` では行ごとの SQL ループになっている。

改善: 変更がある行だけ更新し、必要に応じて中間順位を使って移動行だけ書く。カテゴリは一括 RPC 化。受信イベントを短い単位でまとめ、1 回のキャッシュ更新で適用する。Set / Map による二重走査の削減も行う。500 件のタスク並び替え上限と、初期取得 1,000 件の不整合にも留意する。

将来、同時接続数が増えると Postgres Changes 自体の配信・認可コストも評価対象になる。現在の小規模利用でそこが律速とは断定しない。[Supabase: Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes)

## 8. 初期 JS の重さと初回操作の遅延ロード

根拠: `src/app/page.tsx:7`、`src/components/task/task-list.tsx:4`、`src/components/task/task-item.tsx:4`、本番ビルドの `index.html`。

現代ブラウザ向け初期 script は計 968,681 bytes、gzip 換算 289,422 bytes。JS は転送だけでなく解析・実行が必要になる。この数値にはフレームワーク共通コードも含まれ、すべて削減できるという意味ではない。

TaskList は静的 import で DnD と Motion を含み、Home、FAB、BottomSheet、おすすめにも Motion の利用がある。TaskList だけを dynamic にしても Motion 全体は初期経路から外れない。

作成・詳細・定番品シートの動的 import は入っている。一方、初回にボタンを押してからコードを取得する構造で、専用の loading 表示は指定されていない。低速回線では「押しても開かない」時間が生じうる。これは起動サイズとのトレードオフ。

改善: 軽い通常一覧と DnD 編集機能を分離する案を比較する。単純なアニメーションを CSS に寄せる余地を調べる。使用されそうなシートは主要一覧表示後や pointerdown で先読みし、即座にシートの枠を出す。遅延ロード化だけを目標にせず「最初に操作可能になる時間」を測る。

軽微な点として、ホームで使わない Geist Mono も root layout から preload されている。フォント最適化の優先度は上記より低い。

## 9. 意図的に入れた待ち時間とタブごとの作り直し

根拠: `src/hooks/use-swipeable-tab.ts:179`、`src/app/page.tsx:312`、`src/components/task/task-list.tsx:80`。

横スワイプは指を離した後に 250ms の transition を開始し、transitionend までカテゴリを変更しない。その後 flushSync で新しい一覧を作る。`key={selectedCategoryId}` によって TaskList 自体が再マウントされ、行・DnD・Effect が作り直される。タブを直接タップした場合は、この 250ms の待ちとは別である。

完了操作はチェックを即反映するが、完了セクションへの移動は 300ms 保留する。これ自体は操作の理解を助ける仕様でもあるため、すべてゼロにすればよいわけではない。

改善: 隣接カテゴリの内容を準備して切替アニメーション中に表示する。不要な再マウントを減らす場合、現在 key がリセットしているローカル状態は明示的にリセットする。「応答し始める時間」と「アニメーションが終わる時間」を別に評価する。

## 10. キャッシュ全体の同期保存が長期利用で重くなる

根拠: `src/app/providers.tsx:40`、`src/lib/query-persist.ts:22`、インストール済み `@tanstack/query-sync-storage-persister/src/index.ts`。

成功したクエリを全て永続化し、既定の JSON.stringify + localStorage.setItem、復元時に JSON.parse を使う。古い完了タスクも追加読込した分だけ保存対象になる。

保存にはライブラリ既定の 1 秒の throttle があるため、「1 イベントにつき必ずディスクへ保存」とは言えない。それでも保存・復元のサイズ上限がなく、大きな JSON の処理が UI と同じメインスレッドで走る。端末による実時間は未測定。

改善: 初期表示に必要な最近の軽量データだけ永続化する。キャッシュサイズと所要時間を測り、大きい場合は IndexedDB 等の非同期ストレージも検討する。ストレージを変えても巨大な JSON 変換が無条件に解決するわけではない。

## 11. PWA の再起動をネットワークから切り離せていない

根拠: `public/sw.js:27`。

fetch リスナは respondWith を呼ばず、シェルを保存していない。ブラウザの通常 HTTP キャッシュは利用できるため「毎回すべてをダウンロードする」という意味ではない。ただし SW 側から即座に起動用の画面を返す仕組みはなく、HTML 取得・proxy・認証更新等の待ちを切り離せない。

改善: 再訪起動が重要なら、ユーザーデータを含まないアプリシェルを対象にキャッシュ戦略を設計する。世帯・ユーザーの切替、バージョン更新、ログアウト、オフライン時の認証表示を一緒に検証する。実データ入りページをそのまま使い回す設計にはしない。

## 12. Push の送信経路には直列待ちが残る

根拠: `src/app/api/push/send/route.ts:71`、`src/lib/push.ts:5`。

getUser → 送信者の世帯取得 → 他メンバー取得 → 購読取得 → Web Push 送信という順。通知先への送信自体は並列だが、前段は直列。さらに通常の proxy も API リクエストの対象になる。

ただし呼び出し元は fire-and-forget なので、これを改善してもタスク追加画面の await が直接短縮されるわけではない。通知到着時間とサーバー負荷の改善として扱う。

改善: 認可を維持してメンバーと購読の検索を JOIN / RPC にまとめる。通知先へのタイムアウトやキューを検討する。タスク操作ごとに送信 API を呼ぶ現行頻度も計測する。

## すでに改善済みの点・今回の主要問題から外す点

- React Query のメモリキャッシュ・永続キャッシュ、世帯 ID キャッシュ、Supabase preconnect は導入済み。
- proxy は getClaims、クライアント起動は getSession に変更済み。「起動時に常に getUser が二重に走る」は現在のコードには当てはまらない。getClaims の効果は署名方式、JWKS キャッシュ、有効期限に依存する。
- 初期取得は完了 30 日窓、過去履歴は 30 件ページング。無制限の全期間取得ではない。
- tasks の検索索引、RLS の InitPlan 化、外部キー索引は migrations 015〜018 に存在する。未導入として重ねて指摘しない。本番に適用済みかは別途確認が必要。
- おすすめは 1 年窓かつ 10 分 staleTime、サジェストは最大 500 行・1 時間 staleTime。残る問題は主に呼び出し方と起動時の競合。
- 完了タスク一括削除は DELETE 1 本。タスクの並び替えも HTTP 自体は RPC 1 本で、問題は更新行数とイベント数。
- アバターはアップロード前に 256px へ縮小し、長期キャッシュも指定済み。大画像を毎回そのまま転送する構造ではない。原画像のデコードや全カードの無限アニメーション等には追加の実機検証余地があるが、主画面の毎回の操作より優先度は低い。
- `createBrowserClient` は通常ブラウザでシングルトンを利用する。呼出箇所が多いことだけから、WebSocket 接続がその数だけ増えるとは判断しない。
- `docs/performance-analysis.md` は過去の実装に基づく。getUser、キャッシュ未導入等の記述を現在の課題として使わない。

## 実装・計測の進め方

1. 操作受付と保存完了を分け、作成・編集シートの待ちを減らす。同時に操作時間の計測点を入れる。
2. ハンドラの参照を安定させ、1 行更新時の全行再実行を解消する。
3. 再同期とおすすめ再計算を集約し、1 操作・1 復帰あたりのリクエスト数を減らす。
4. 一覧・詳細のデータ分離、履歴ページング、変更行だけの並び替えを進める。
5. 実機で初期 JS の処理時間を測り、DnD / Motion / 遅延ロードの設計を調整する。
6. キャッシュなし起動には bootstrap、再訪起動にはシェルキャッシュをそれぞれ比較する。

測定は本番ビルドを使い、未完了 20 / 100 / 500 件、履歴 1 千 / 1 万 / 5 万件、短いメモ / 長いメモ、キャッシュなし / 再起動 / スリープ復帰で分ける。中級スマートフォン、遅延のある回線、二端末の同時操作を含める。

「爆速」の暫定目標例は、通常操作の見た目の応答 p95 100ms 以内、キャッシュ再訪で操作可能になるまで p95 500ms 以内。これは達成済みの数値でも一般規格でもなく、端末・回線条件を固定して合意する製品目標である。Web Vitals だけでなく、タスク表示完了、シート入力可能、チェック即時反映、相手端末への反映を個別に計測する。

ソースには Web Vitals / performance.mark / PerformanceObserver 等の独自計測が見当たらない。ホスティング側の計測有無は未確認。SQL は代表的なデータ量で EXPLAIN (ANALYZE, BUFFERS) と呼び出し回数を測り、リージョン・署名キー・migration 適用状況も確認して、初めて本番の律速箇所を確定できる。
